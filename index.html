Design rule: code computes, the model only narrates

      
Early tests showed every small local model corrupting or inventing numbers it was asked to copy. So the model never touches a number: code parses, counts and groups the alerts; the model gets numbered rows and returns strict JSON (id, verdict, one-line reason); code validates the answer, applies safety rules and writes the report.

Honest result: the value is mostly in the code around the model: noise removal, new-today and priority flags, mechanical checks of server responses, and a guard against calling attacks benign. The model adds a plain-language reason per row; it is not the decision maker.


      
Case study: from IDS alert to network redesign

      
Within hours of opening ports 80/443 for a public site, the IDS showed reputation-list sources, a GraphQL introspection probe and requests for /.env, phpinfo and wp-config backups. All got 404, but the site answered from the Admin VLAN, so anything that got through would start inside the trusted segment. The DMZ plan that followed notes a trap: moving only the public IP to a new VLAN looks like a DMZ on a diagram but isn't one, because the pod still runs on an Admin-VLAN node. Real isolation means moving the node that handles untrusted input.

Triage runbooks

      

        

          Encoded PowerShell execution
          
    
            
  1. Confirm powershell.exe with -EncodedCommand; record time, host, user and parent process.
    2. 
            
  2. Decode the Base64 payload and work out what it does (runs scripts, downloads files, changes settings).
    3. 
            
  3. Look for child processes, IEX / Invoke-Expression or chained commands that point to a multi-stage attack.
    4. 
            
  4. Check context: is this user or script expected to do this, and on what kind of system?
    5. 
            
  5. Look for related activity: more PowerShell, outbound connections, new scheduled tasks or registry changes.
    6. 
            
  6. Escalate if it is unexpected; mark it informational if it is authorized administration or testing.
    7. 
          

        

        

          Multiple failed logons
          
    
            
  1. Pull Event ID 4625 and count attempts in the time window.
    2. 
            
  2. Identify the source and whether it targets one account or many.
    3. 
            
  3. Check for a successful logon (Event ID 4624) after the failures.
    4. 
            
  4. Compare the timing and pattern with this user's or system's normal behavior.
    5. 
            
  5. Escalate or block the source if it looks malicious; mark it informational if it was user error.
